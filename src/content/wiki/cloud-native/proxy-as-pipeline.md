## 一句话本质
**代理的稳定性来自「不解析业务报文」——只搬运字节，就与协议演进彻底解耦；一旦开始解析，就被绑到某个协议版本上，从此跟着上游跑。**

## 方法要点

- **不解析的红利**：上游换协议版本（如 git v2 引入 `Git-Protocol` 头）、加新命令、改报文格式，管道一行代码都不用动。
- **但有三件事逼你「看内容」**：① 失败回退（要先知道这次到底成不成功）；② 内容级校验（**状态码 200 不等于成功**，错误常包在响应体里）；③ 凭据替换（要识别鉴权头）。完全闭眼的代理是理想，不是现实。
- **判据：区分「必须看的」和「想看的」，能给「看」加边界的就加边界**——只看响应**开头**（状态码 + 首段报文）就能覆盖绝大部分早期错误，且不牺牲流式。
- **回退 vs 流式的内在矛盾**：流式要求"不缓冲、边收边发"，回退要求"转发前就知道结果"——调和点只有一个：**只看开头**。错误在时间轴上的位置决定可回退性：响应头/首段错误 → 可回退；转发到一半才发现 / 传输已中断 → **回不去了**。
- **代价守恒**：要回退就得能**重放请求体**（缓存请求体 = 内存成本），或者**重新构造请求**（要解析语义 = 从管道变解析器）。选哪个，取决于能接受多少内存、以及要不要保住「管道」的纯粹性。
- **fail-safe 收口**：凡是"判断不出来"的情况，一律落到安全侧（例如只有明确状态才走快路径，其余走兼容路径）。**白名单，不是枚举例外。**

## 记住点
不解析就与协议解耦；要看就只看开头；回退与流式天然互斥，靠「只看开头」共存。
