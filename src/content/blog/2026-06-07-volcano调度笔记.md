## 概念

Volcano 是 K8s 中的容器批量调度平台，基于 kube-batch 演进而来。它提供 gang 调度、公平分配、抢占、拓扑感知等多种能力，特别适合 AI 训练、大数据等需要多 Pod 协同的场景。

核心特性是 **gang 调度**：一组 Pod 要么全部调度成功，要么全部等待。避免了分布式训练中部分 worker 启动、部分卡在 Pending 的尴尬。

## 调度策略

- **Gang Scheduling**：确保作业的所有任务同时启动
- **DRF Scheduling**：多维度资源公平调度，"谁要的资源少，谁的优先级高"
- **Binpack**：尽量把任务塞满节点，提高资源利用率
- **Preemption/Reclaim**：高优先级任务可以抢占/回收低优先级任务的资源
- **Task-topology**：任务拓扑感知调度，优化通信密集型应用性能
- **NUMA Aware**：NUMA 架构感知，优化多核资源分配
- **NodeGroup**：节点分组亲和性调度

> 我用到的是 gang scheduling，保证多个 Job 同时被调度。

## 与 K8s 的交互机制

Volcano **不是替代** kube-scheduler，而是通过 `schedulerName` 字段"认领"特定 Pod。

### 接管 Pod

```yaml
spec:
  schedulerName: volcano  # 声明由 Volcano 调度
```

K8s 允许多调度器共存。Pod 的 `schedulerName` 默认为 `default-scheduler`，设为 `volcano` 后，K8s 内置调度器就不再管它。

### 两条数据流

**读（集群 → Volcano）—— Informer 机制**：

不是轮询，是长连接推送。Volcano 注册了 18 种 Informer（Pod、Node、PodGroup、Queue、PVC、CSI 等），每种绑定 Add/Update/Delete 三个回调。K8s API Server 通过 HTTP Chunked Stream 实时推送变化。

```go
// 关键代码：cache/cache.go 第 707 行
sc.podInformer.Informer().AddEventHandler(
    cache.FilteringResourceEventHandler{
        FilterFunc: func(obj interface{}) bool {
            pod := obj.(*v1.Pod)
            // 只认 schedulerName=volcano 的 Pod，其余的丢弃
            if !responsibleForPod(pod, sc.schedulerNames, ...) {
                return false
            }
            return true
        },
        Handler: ...{ AddFunc: sc.AddPod },
    },
)
```

**写（Volcano → 集群）—— Binding API**：

调度决策完成后，调用 K8s 标准 Binding API，告知 API Server "这个 Pod 放这个 Node"：

```go
// 关键代码：cache/cache.go 第 236 行
db.kubeclient.CoreV1().Pods(p.Namespace).Bind(ctx,
    &v1.Binding{
        Target: v1.ObjectReference{
            Kind: "Node",
            Name: task.NodeName,  // 调度决策选好的节点
        },
    }, metav1.CreateOptions{})
```

等价于：
```bash
curl -X POST /api/v1/namespaces/default/pods/my-pod/binding \
  -d '{"target":{"kind":"Node","name":"node-3"}}'
```

随后 Kubelet 看到 Pod 绑定了自己的 Node，启动容器。

### 完整链路

```
Pod 创建(schedulerName=volcano)
      │
K8s 默认调度器 → 看到 schedulerName≠default → 跳过
Volcano Informer → 过滤 schedulerName=volcano → AddPod → 进 Cache
      │
runOnce() 触发
      │
拍快照(Snapshot) → Session → Action(allocate/preempt) → Plugin(gang/drf)
      │
找到合适 Node → Statement.Pipeline() → AddBindTask()
      │
BindTask() → DefaultBinder.Bind() → POST /api/.../binding
      │
Kubelet 启动容器
```

## 调度原理

### Session 快照模式

Volcano 调度不是"来一个 Pod 处理一个"，而是**定时拍快照、统一决策**。

```go
// scheduler.go 第 124 行
func (pc *Scheduler) runOnce() {
    ssn := framework.OpenSession(pc.cache, plugins, configurations)  // 拍快照
    
    for _, action := range actions {
        action.Execute(ssn)  // 按序执行 enqueue → allocate → preempt → ...
    }
    
    framework.CloseSession(ssn)  // 提交结果
}
```

为什么拍快照而不是实时决策？和数据库事务一个道理——**乐观并发控制**。一次性读所有 Pod + Node 状态，在内存中规划好，一次性写回，避免中途状态变化导致冲突。

### Action-Plugin 分离

这是 Volcano 最巧妙的设计：

```go
// framework/interface.go — 两个核心接口
type Action interface {
    Execute(ssn *Session)  // "做什么"：allocate、preempt、backfill...
}

type Plugin interface {
    OnSessionOpen(ssn *Session)   // Session 开始时：gang 检查 minMember
    OnSessionClose(ssn *Session)  // Session 结束时：清理
}
```

| | Action | Plugin |
|--|--------|--------|
| 职责 | **做什么**（分配、抢占、回收） | **怎么判断**（够不够资源、优先级谁高、是否符合 gang 约束） |
| 举例 | allocate、preempt、enqueue、reclaim | gang、drf、priority、binpack、predicates |
| 关系 | 一个 Action 调用多个 Plugin 来判断 | 多个 Action 复合同一批 Plugin |

**好处**：策略可以自由组合。比如想用"先分配再抢占"的流程，配置 `actions: [enqueue, allocate, preempt]`；想用"只分配不抢占"就去掉 preempt。Plugin 也一样——不想用 DRF 就从配置里移除。

### 默认调度管道

```
enqueue → allocate → backfill → preempt → reclaim
  入队      分配       填补碎片    抢占      回收
```

每个 Action 遍历 `Queue → Job → Task → Node`，调用 Plugin 判断是否可调度，找到后通过 `Statement.Pipeline(task, nodeName)` 发起绑定。

## Volcano 结构

![系统架构](/src/content/blog/2026-06-07-volcano调度笔记/1173617-20251120010102985-896309725.png)

四个组件：

- **Scheduler**：核心调度器。通过 Action + Plugin 调度 Job，找到最适合的节点。与 K8s default-scheduler 不同，它**支持批量和 gang 调度**。
- **Controller Manager**：管理 CRD 资源的生命周期（Queue、PodGroup、VolcanoJob）
- **Admission**：对 CRD API 资源进行校验和变更（如自动给 Pod 注入 PodGroup 注解）
- **Vcctl**：命令行客户端工具

## 核心概念

### Queue

队列用于管理和优先级排序任务。不同业务可以分到不同队列，控制资源分配和调度优先级。

### PodGroup

一组相关的 Pod 集合。这是 gang 调度的核心——Volcano 以 PodGroup 为单位判断"是否所有 Pod 都能同时调度"。

### VolcanoJob

扩展了 K8s Job 资源，加入对批处理作业的额外支持（minAvailable、queue、priority 等）。

## 使用

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  annotations:
    scheduling.volcano.sh/group-min-member: "2"  # 至少 2 个 Pod 一起调度
spec:
  replicas: 3
  template:
    spec:
      schedulerName: volcano  # 关键：使用 Volcano 调度器
      containers:
        - name: my-container
          image: busybox
          command: ["sh", "-c", "sleep 3600"]
          resources:
            requests: { cpu: 1 }
            limits: { cpu: 1 }
```

几个关键点：

- `annotations` 中 `group-min-member` 控制 gang 调度的最小 Pod 数
- `spec.template.schedulerName: volcano` 才能走 Volcano 调度。我在 GitLab Runner 里一开始就漏了这个，一直没调度成功
- 通过 `kubectl get pg` 查看 PodGroup 状态
